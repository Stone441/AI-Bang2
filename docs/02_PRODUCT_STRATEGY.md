# 推荐方案：让团队更快得到可以核对、可以安全使用的答案

> 版本：1.0｜性质：**团队候选方案与执行建议，不是官方新增要求，也不保证获奖。**  
> 官方事实唯一入口：[01_OFFICIAL_BRIEF.md](01_OFFICIAL_BRIEF.md)。本文所有指标和范围如未注明官方来源，均为待验证的团队目标。

## 1. 一句话定位

**面向工程、产品和运营的内部知识助手：连接Confluence、Jira、Slack、Google Drive，把分散资料变成有证据的工作答案，并在资料更新和权限变化后继续保持可信。**

工作名候选：**ContextLedger**。这是团队可修改的暂定名字，不是Aspire官方产品名，也未进行商标/同名核查。选题正式名称仍使用官方的 **The Internal Brain**。

提交短介绍候选（8个英文词）：

> Trusted answers across tools, backed by verifiable evidence.

我们要证明三件事：**少找资料、少等同事；知道回答依据什么及是否足够新；无权读取的信息不会经由AI被绕过权限。**

**不改成另一个大产品。** 产品、运营和工程使用同一套资料与同一个检索/权限引擎，只改变问题和答案表达方式。

## 3. 场景选择：一个业务世界，两类工作任务

### 3.1 统一演示主题

采用合成的 **payment-service发布、事故与能力边界** 场景。资料明确标记为虚构测试数据，不冒充Aspire内部文件。

工程师问：

> What caused the last payment-service incident, which follow-up tickets are still open, and which runbook should I use now?

产品或运营问：

> Can we offer the new payment-retry capability to customers today? What is supported, what is still limited, and who owns the next step?

第二个问题必须基于已授权的产品说明、发布记录和可见任务回答。**Jira的Done不自动等于功能已对客户GA，工程师的Slack猜测不自动等于正式承诺。** 当可见证据不足时，只给出已确认范围与待确认的问题，不补出商业承诺。

### 3.2 “之前—之后”工作流程

当前待验证的假设流程：在四个平台搜索 → 逐一核对资料版本 → 找到相关负责人 → 等待解释 → 汇总结果 → 再去核对。

目标流程：提出工作问题 → 看到简明答案、未解决事项和证据 → 点击关键结论核对 → 知道是否需要找人继续确认。

不把资料所有权迁进这个新系统；源平台仍是内容和权限的权威来源。本产品解决上下文获取，不取代Confluence/Jira/Slack/Drive本身。

### 3.3 要真实验证的业务问题

在赛道群或能联系到的企业代表处争取获得三组真实查找案例，重点询问：

- 最近一次跨平台找信息，起因、路径、耗时、最终依据和需要找的人是什么？
- 工程与产品/运营最常见的误解，是找不到、过期、缺少背景，还是不知道哪个来源有权威性？
- 哪些任务必须很新，哪些敏感资料最容易出现权限差异？
- “回答对了”怎么判定？哪些内容即使存在，也不应该被这个系统收集？

没有真实访谈时，把这些写为假设，不生成“访谈发现”或“客户认可”。不假设Aspire会开放公司内部数据。

## 4. 三个值得投入的差异化能力

### 4.1 答案附带一张可核查的证据卡（Answer Receipt）

每次回答同时提供：

| 展示元素 | 帮助用户判断什么 |
|---|---|
| 关键结论对应证据 | 这句话依据哪一段原文，而不只是页面底部一串链接 |
| 来源、文档/消息定位、版本 | 能打开核对并知道使用了哪个版本 |
| 来源更新时间、最近成功同步时间 | 区分“资料本身较早”与“系统没有及时同步” |
| 当前回答范围 | 哪些问题有证据支持，哪些无法确认；不展示隐藏资料数量 |
| 请求编号 | 便于反馈和审计追踪，但不是持有编号就能查看日志的通行证 |

“证据卡”是展示结构，不是外部认证或数学保证。引用存在与语义支持必须分开测试。普通用户不得在卡片中看到拒绝文档标题、隐藏结果数量、其他人的权限或后台错误细节。

### 4.2 同一问题，在变化发生后仍然答对

演示不仅是不同账号返回不同内容，还包括：

1. 有权限用户查询，得到带证据的答案。
2. 源平台移除其权限，**不重建全部向量**。
3. 原用户在同一会话里追问，系统重新授权，不从旧会话、缓存或引用接口继续读出受限内容。
4. 资料所有者更新应急步骤，后台增量处理，下一次查询引用新版本。

这把权限和新鲜度从“宣称有”变成“评委可以观察到”。四个来源均要有对应的可复现验证；台上为节约时间可以重点展示其中一个，其他保留实测记录和worked examples。

### 4.3 精确的审计询问和可验证日志

审计员用自然语言提出查询，看到经过授权的精确记录表、时间范围、分页和日志完整性状态。

再在**日志副本**中修改一条事件、删除被可信检查点覆盖的尾部，运行独立校验器展示失败。原始记录保持不动。

重要界限：这证明特定威胁模型下能发现变化，不等于任何管理员都无法篡改，也不等于知道员工绕开本产品在四个平台里的全部访问。

## 5. MVP、展示增强、延期项

### 5.1 提交前必须形成证据的部分

以下为团队优先级，不改写官方要求：

| 优先级 | 能力 | 验收形态 |
|---|---|---|
| P0 | 四源统一数据模型与检索；源权限差异不丢失 | 每源至少一次端到端演示；标明live / mock / fixture和覆盖限制 |
| P0 | 服务端身份、模型前鉴权、动态撤权 | 无权限文本不进入回答/重排模型；同角色不同成员关系可测 |
| P0 | 有界增量更新、删除/失去访问处理 | 可复现事件时间线、实际延迟、版本变更 |
| P0 | 关键结论引用、缺证据时不补事实 | worked examples与引用支持测试 |
| P0 | 完整、可查询、可检测篡改的审计 | 逐文档授权事件、最终答案、独立校验 |
| P0 | 真实CodeBuddy/WorkBuddy贡献与记录 | 代码/测试/分析产物、commit或文件、真实对话、至少3张截图 |
| P0 | 官方所需材料 | 描述、短介绍、封面、架构/信任边界图、源码、五场景示例 |
| P1 | 证据侧栏、状态提示、流畅的工程与产品问答体验 | UI walkthrough |
| P1 | 5–8分钟demo video及可访问部署 | 虽官方部分为optional，作为内部提交目标；不得牺牲P0安全 |
| P1 | 小规模真实任务对照测量 | 时间到已验证答案、质量和成本表 |
| P2 | 反馈分类和回归闭环 | 有1–2个真实坏案例改进记录，而非空白“自学习”按钮 |

**“四源有适配器代码”不等于“四源集成已完成”。** 缺API或权限时继续用fixture开发，但维护逐源能力表；未获主办方同意，mock不得被写成符合真实集成要求的等价替代。

### 5.2 首版明确不做

不做资金操作、自动部署、自动修改业务工单或文档；不建设全公司知识图谱；不默认采集所有DM；不加第五个来源Notion连接器；不做多租户SaaS商业化后台；不训练专用路由模型；不微调金融模型；不加区块链或复杂多Agent辩论；不以未经审批的反馈自动更新正式知识。

不禁用合理改进。Codex发现简单方案无法达到已定义测试时，提出小范围替代及证据，再变更。

## 6. 页面结构：少页面，但每页承担清楚的职责

### 6.1 Workspace：员工使用

上方为实际登录身份；开发演示账号切换仅允许在明确的合成数据demo环境。主体是问题与回答，旁侧为可展开证据。对每条关键结论有引用入口，显示来源更新时间与使用版本。

回答优先结构：**直接答案 → 事实依据 → 未解决/无法确认的部分 → 需要联系谁或核对什么**。只有证据支持时才能给负责人，不能从受限资料推断。

默认英文产品界面和demo问题，团队文档中文。支持键盘操作、可读对比度、合理字号，状态提示不只依赖颜色。不要堆出过多管理员按钮让普通用户困惑。

### 6.2 Sources：受限的连接器/同步视图

显示经授权管理者可见的连接状态、覆盖范围、最后成功checkpoint、积压、限流和同步异常。普通用户仅显示其授权范围内、不会泄露受限来源存在性的信息。

### 6.3 Audit：独立授权的审计视图

自然语言转结构化条件；清晰显示实际筛选条件与时区、记录表和分页；需要时查看被授权的事件详情。区分candidate、authorized、sent_to_model、cited和response_dispatch，避免将它们统称“读过”。

### 6.4 Feedback：轻量回归入口

反馈“过期、证据不支持、遗漏、问题没答到”等，并关联请求ID。先形成可复现问题，再修复测试和逻辑，不直接入库成为新的事实。

## 7. 数据制备原则

先定义完整事实清单和角色权限矩阵，再把它展开成四个平台的资料。保持实体ID、时间线、工单链接和版本一致；刻意保留旧猜测、后续澄清与正式发布说明。

详见[验收与数据设计](05_ACCEPTANCE_TESTS.md)。首批可以只做12份核心资料、6类用户，打通后扩充到约40–60个对象；这些是规模建议，不是官方最低量。

建议把合成资料写入**团队有权管理的真实测试workspaces**，以实测真实API与权限行为。写入源平台、创建账号、申请较高权限、产生费用，都由人确认。系统运行时仍只读；测试资料种植脚本与普通问答链路隔离。

数据获取失败时，不静默用随机文本替代；如实记录该连接器状态和替代测试范围。转写提到Notion反映公司平台多样性，但本题四源范围仍按手册。

## 8. 指标：先定义测量，再决定是否保留优化

| 指标 | 团队初始目标/报告方式 | 为什么这样测 |
|---|---|---|
| Time to verified answer | 对同类任务测“找到且核对正确答案”的时间，报告中位数和失败次数 | 不能把快速生成一段错误文本算效率提升 |
| 回答延迟 | 在明确模型/硬件/网络、如3并发条件下，争取常见问题p95≤15s；未达标如实报告 | 权限查询与重排也计入；此数值不是官方SLA |
| 内容可查询延迟 | 团队目标：正常测试条件每次变更≤5min；超过5min明确告警；30min作为需调查的风险线 | 比现场关注窗口更短，但只能以实际测量为成果；p95不替代最大值 |
| 撤权 | 权威源已反映撤权后的下一请求不使用该资料；权限无法确认时不放行 | 不承诺跨平台毫秒级原子一致性 |
| 引用支持 | 固定测试中关键事实均有证据且证据支持；显示总条数和失败例 | 不是只看引用URL是否存在 |
| 安全回归 | 所定义的隔离/撤权用例全部通过，报告覆盖范围 | “测试中零泄露”不等于普遍零风险 |
| 每次成功任务成本 | 模型、embedding摊销、源API/托管成本分列 | 不把开发工具credits当作运行成本为零 |
| 更新成本 | 更新一个对象所处理的对象/块数、时间、向量重算数 | 证明无需全库重建 |

成本和ROI的计算框架属于团队估算方法，不是Aspire已验证数据：

```text
单任务节约时间 = 人工查找并验证耗时 - 系统辅助并验证耗时
月度可释放工时 = 每月适用任务量 × 单任务节约分钟 ÷ 60 × 实际采用率
估算净价值 = 可释放工时 × 明确假设的小时成本 - 月运行成本
```

把“释放工时”与“实际减少现金支出”分开。没有客户的任务量或时薪数据，就报告小样本实验结果与假设区间，不编造全年节约金额。

小型用户验证建议：找3–5位未编写测试资料的同学，每人完成一组短任务；使用不同但难度近似的任务、交换实验顺序减轻学习效应。记录样本和方法，不做统计显著性或企业可推广性保证。作者自测和非作者测试分开。

## 11. 面向团队的取舍与授权

Codex负责分解方案、提出架构、实现、运行测试、修复和整合；这份文档给它一个可挑战的默认方向，不把某种框架锁死。

三位成员保留的责任：确认目标用户/业务假设；开通并授权账号与预算；核对权限与数据边界；观看关键场景实际运行；批准对外陈述与提交。学位和专业不能替代实际技术验证，也不意味着必须按专业划分代码模块。

建议Kyle重点推动业务场景、跨角色问题和总体集成验收；另外两位按实测开发熟悉度分担数据/同步与权限/审计。所有角色均为建议，尚未由本人确认。

**成功路径是让同一份小而真实的业务上下文，在不同人、不同时间和不同权限下都能正确使用。** 安全、新鲜度、引用、审计是这个工作流程的一部分，而不是单独堆在后台的展示按钮。
