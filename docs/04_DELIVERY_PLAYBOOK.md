# 交付路线、三人协作与编码Agent执行手册

> 状态：**执行计划，不是完成报告。** 本文日期、任务分工和工具任务为团队建议；官方规则只以[01](01_OFFICIAL_BRIEF.md)及后续经核实的澄清为依据。  
> 输入：[产品方案](02_PRODUCT_STRATEGY.md)、[架构](03_ARCHITECTURE.md)、[验收](05_ACCEPTANCE_TESTS.md)。

## 1. 工作方式：Codex主导实现，人控制目标和关键授权

Codex可以在已批准范围内完成设计细化、编码、测试、修复、文档和集成，不必把每一个函数、库选择或界面微调都交给人决定。三位成员不是逐行代写代码，而是决定目标是否正确、验证产品是否真的满足场景，并对账号、费用、数据和对外发布负责。

本包允许Codex先做**本地、可逆、无外部写入和新增费用**的Phase 0准备。其后的运行权限来自团队在当前开发环境中的明确授权，不来自文档中的一句“全自动”。

| 决策 | Codex可自行推进 | 需要人确认 |
|---|---|---|
| 常规实现 | 模块内部结构、类型、测试、依赖现有能力的小型重构 | 替换已确定的核心栈导致明显返工、引入新外部服务 |
| 数据与权限 | 使用本地合成fixture、实现适配器、验证既有授权内的只读调用 | 新建/修改外部测试资料、申请scope、接入真实个人或企业数据、降低权限标准 |
| 模型和基础设施 | 使用已批准的provider和预算；没有可用模型时实现fake provider | 新开收费、切换数据传输地区、使用未经批准的第三方模型或追踪服务 |
| 协作 | 独立分支、worktree、局部提交、PR草案 | 覆盖别人未提交工作、强推、删分支、合并受保护主线（除非已有明确授权） |
| 产品与评测 | 修复失败、增加案例、报告限制 | 改写官方要求、删安全测试以通过验收、承诺未经实测的能力 |
| 发布 | 生成候选版本和本地演示材料 | 公开部署、开仓库权限、上传聊天证据、最终提交比赛 |

## 2. 只设三个正式批准关口

**G0：范围与接入确认。** Phase 0完成后，人确认主场景、模型/费用边界、四源测试环境和可接受的暂时模拟范围。若连接器条件尚未齐全，允许先推进本地闭环，但不能将live集成标记完成。

**G1：对外开放前的安全核验。** 人实际观看负面权限、同会话撤权、引用访问与日志校验演示；确认测试环境只含合成资料、公开入口不暴露管理员操作、密钥不进入仓库或录屏。未过G1不对外开放。

**G2：最终交付与陈述核验。** 人对照提交清单确认材料、实测数字、限制说明、CodeBuddy/WorkBuddy真实贡献及评委访问方式，批准发布和提交。

G0与G1之间，已批准里程碑中的普通任务由Codex连续推进。每天只需一个短检查点：**已验证什么、正在做什么、卡在哪里、最多三项需要人决定的事。** 遇到安全失败立即报告，不必等日报。

## 3. 第一阶段首先消除接入风险

不要先做精美聊天界面，再发现无法代表用户检查Slack或Drive权限。最初应为每个平台维护能力表：

| 字段 | 必须填写的实际证据 |
|---|---|
| 测试环境 | 团队控制的workspace/site/drive及用途；不得在公开文档放敏感标识 |
| 认证方式 | 用户委托token、应用token、可用scope；谁负责授权 |
| 全量读取 | 实际读取的资源类型和分页结果 |
| 内容变化 | 事件、change token或轮询，重复/漏事件处理 |
| 当前权限 | 以目标用户身份确认读取的办法；平台限制；是否已实测撤权 |
| 细粒度范围 | 页面、工单/评论、频道/线程、文件/父目录继承的覆盖 |
| 限流与失败 | 超时、429、权限无法确认时的行为 |
| 状态 | `not_started / fixture_only / live_partial / live_verified / blocked` |
| 证据 | 测试命令、时间、结果文件、commit；不能只写“文档上支持” |

**不要把四源接入简化成拿到四个服务账号token。** 服务账号可读取全库，未必能验证某个员工的当前权利。接口名称和scope以实现当日官方文档及测试结果为准。[技术依据见03第5、8、15节]

最初24小时内，由一名队员把[01第12节](01_OFFICIAL_BRIEF.md)中的关键问题发到赛道群：数据/沙箱、mock接受范围、混用开发工具、评分细则、提交时间。Codex可以起草，不擅自替团队发送。没有答复时，本地合成数据开发继续进行，相关验收保留blocked。

## 6. 三人、多个Agent如何避免互相覆盖

GitHub保存代码、方案、测试和状态，是团队协作的事实入口；不要依赖某一位的聊天窗口持有唯一架构决定。第一天确认一个集成人，由其Codex工作区维护公共契约和主线集成。

默认三条工作线：数据/同步；身份/权限/审计；问答/界面/集成。谁负责哪条由实际经验与意愿决定，不能仅凭学位标签分配。

使用独立任务分支与独立工作目录/worktree，禁止Codex和CodeBuddy同时编辑同一份未提交文件。跨工作线修改共享schema、API、身份模型时，先在任务中提出接口变更，再更新契约和测试。Agent可以做独立审查，但“另一个Agent说没问题”不等于已验证。

每次交接应只有一个短任务包：

```text
任务ID / 当前分支与基准commit
目标、非目标、允许修改的路径
接口与数据契约
相关官方要求ID、验收测试ID
允许使用的凭据/预算（不包含密钥本身）
期望交付：代码、测试、实际执行记录、未解决问题
禁止修改/可能冲突的文件
```

Git提交前检查变更范围和密钥。不要预设远端分支保护或CI已开启：Codex应先检查；没有设置权限时报告。项目现有`README.md`应增量编辑，不用本包覆盖；已有`Requirements`材料保留，用户明确排除的GPT生成文件不作为需求依据。

## 7. CodeBuddy：具体使用环节与可直接复制的任务

### 7.1 先让工具真正加载同一份上下文

Kickoff介绍了VS Code/JetBrains插件、桌面和CLI，但当前账号具体界面需本人确认。CodeBuddy官方IDE Rules文档描述了项目规则以及`AGENTS.md`兼容机制；这不证明每一种插件版本自动加载行为相同。[外部技术来源：03 T12]

稳妥办法：在所用CodeBuddy入口显式附加根`AGENTS.md`、任务涉及的03/05章节及接口代码，请它先列出加载到的约束。不能认为Codex的会话自动被CodeBuddy继承。不得共享个人登录或把订阅token粘贴给队员。

### 7.2 任务一：增量同步，形成实质代码贡献

在DEV-02/03接口确定后使用：

```text
这是Tencent AI CAN DO IT Hackathon的Aspire Internal Brain项目。
先读AGENTS.md、docs/03_ARCHITECTURE.md第4–6节、
docs/05_ACCEPTANCE_TESTS.md的F组，并读当前SourceAdapter与数据库契约。

你的任务是DEV-05：实现可测试的增量同步组件。
只处理本任务分支上的ingestion模块及其测试，不改变登录、授权策略、检索和前端。
要求：对象级版本识别、事件去重、重试、旧版本事件处理、删除停用、
新版本准备好后原子切换，以及权限变化不触发正文embedding重建。
先以确定性的本地fake source实现测试；未获授权不调用外部写API或收费服务。
复用已有契约；若契约不够，先明确提出变更，不创建一套相互不兼容的schema。

完成后实际运行允许的测试，报告命令、结果、修改文件和仍未覆盖的失败模式。
不能把未运行的测试称为通过。保留本次对话，供真实工具使用证明。
```

### 7.3 任务二：独立安全回归，避免“自己证明自己”

```text
先读AGENTS.md、docs/03_ARCHITECTURE.md第8–11节和
 docs/05_ACCEPTANCE_TESTS.md的P组、A组。审查当前实现，不放宽既有约束。

在单独测试分支构造：同角色不同频道权限、源端撤权而本地ACL未更新、
同会话追问、缓存命中、引用/导出端点、受限评论、授权超时、日志写入失败。
捕获所有问答链路的模型输入，证明无权内容没有进入回答、重排或压缩模型。
同时检验日志修改、中间删除、已被独立检查点覆盖的尾部删除能否被发现。
先提交可复现失败测试和原因；不为让测试变绿而删除断言或改成默认允许。
只修改约定测试路径。需要实现修复时，给出最小补丁建议交给集成人确认。
如当前架构不具备真实独立检查点，请明确报告，不能在测试中伪装成独立信任根。
```

对话中的测试建议可以很有价值，但至少安排一个产生真实实现或实质修复的CodeBuddy任务；对外按实际贡献描述，不称CodeBuddy独立完成整套系统。

### 7.4 备选：证据侧栏或单一连接器

当同步已由其他人开始且不宜抢任务时，CodeBuddy可在独立目录实现证据侧栏及键盘可访问测试，或实现一个已验证API的连接器。任务必须指明输入类型、真实API边界、授权要求和不得显示的隐藏元数据。

## 8. WorkBuddy：适合做什么、不要依赖什么

WorkBuddy不是必选，因为官方至少使用CodeBuddy或WorkBuddy之一即可；它可以承担真实的非编码工作，不要求为了使用而强行把后端迁过去。[官方依据：01第7、8节]

建议三个任务按需选择：

| 环节 | 输入 | 应交付的真实产物 |
|---|---|---|
| 需求/材料核对 | 01官方汇编、当前项目说明、提交清单 | 缺漏表，逐项说明source与状态；不能编造新规则 |
| 合成资料一致性检查 | 真值清单、12对象/扩展资料、用户矩阵 | 冲突报告：版本、时间、工单状态、负责人、权限；不是随机造数据 |
| 业务测量与讲述 | 实际测试结果CSV/JSON、方法、限制 | 真实样本ROI分析、7分钟脚本、项目描述草稿 |

可复制任务：

```text
读取docs/01_OFFICIAL_BRIEF.md、docs/02_PRODUCT_STRATEGY.md，以及我提供的实际评测结果。
你的任务是核查并起草提交说明，不实现系统、不向外部发送或发布。
将内容明确分为：官方要求、已实现且有证据、部分实现、未验证、下一步计划。
每条指标引用输入记录；没有数据的格子保留“未测量”，不要自动补数。
检查SUB-01至SUB-09及Aspire A-16，另列缺少的对话记录、截图、worked examples和架构图。
短介绍严格少于10个英文词。演示录像按5–8分钟草拟，不能把它称为现场强制时长。
输出可存入GitHub的Markdown，保留相关输入文件与结果文件的对应关系。
```

WorkBuddy Projects在Kickoff中是10月初上线的预告，**不作为协作或交付的前置依赖**。当前可用则试用共享项目指令与资料；不可用就显式传文件并回存GitHub。不假设它能自动访问私有仓库或本地Codex会话。

## 9. 腾讯工具使用证据要从现在开始积累

建议由一位成员负责`evidence/tool-usage/`，该目录由实现阶段创建。对话和截图涉及个人信息/密钥时先脱敏，未经批准不要公开；记录脱敏范围，不改写结果和时间线。

每次有效使用建立记录：工具与入口、操作者、时间、任务ID、相关输入、产物路径、commit/PR、测试记录、原对话导出位置、截图。某字段没有则写`not_available`，不得造API日志或截图。

**至少保留三次有意义的过程画面**，例如：需求/接口理解、实现或调试、实际验证结果。截图数量不替代手册另行要求的Conversation History；保留完整可导出记录，提交节选或脱敏是否接受另行确认。

以下证据不合格：由Codex生成一张看起来像CodeBuddy的聊天截图；事后编写“CodeBuddy完成了某模块”但实际未使用；把他人的对话当作本队贡献；把工具界面可选GPT模型理解为可以使用Codex订阅额度。

## 10. 环境、预算与运行能力分开管理

**开发工具订阅/赛事credits**支持开发，不自动赋予你们应用调用模型API、embedding或云托管的额度。ChatGPT与API平台是独立计费体系，实际runtime需要单独批准的凭据和预算。[外部技术来源：03 T13]

Phase 0应提供`.env.example`占位变量，真实密钥留在被忽略的本地环境或获批密钥系统。未提供runtime凭据时，先让fake provider支撑集成测试，真实LLM效果测试保持not_run。

由团队明确预算上限和数据范围；Codex实现单请求token/耗时限制、重试上限、预算监控，不无限重跑模型或重复embedding。新增付费动作默认不获授权；已批准provider的范围内是否可调用，由当前任务授权决定。

让Codex提供少而明确的统一入口，例如`make setup`、`make test`、`make demo`、`make verify-audit`。**这些是建议它实现的命令，不是本包已经存在、现在就能执行的程序。** 如选择其他工具链，提供等价、可复制、实测命令。

## 11. 每次迭代要留下的最小记录

首次启动时由Codex按真实仓库状态创建：

- `docs/STATUS.md`：当前阶段、commit、live能力矩阵、最新已运行测试、blockers、下一步、人类待决事项。
- `docs/BACKLOG.md`：DEV任务及依赖，状态为not_started/in_progress/blocked/verified；带相关测试ID。
- `docs/DECISIONS.md`：重要ADR、替代方案、选择理由、证据、批准状态。
- `evidence/`：测试结果、真实工具贡献、demo材料的索引；敏感附件不默认入公开Git。

这些文件尚未随本包预填完成状态，避免“计划”变成伪造的进度记录。状态更新不要重复整份架构，只记录变化和证据。

任务结束输出：**做了什么 → 实际执行什么验证 → 结果/限制 → 修改路径或commit → 下一项任务。** 若在允许范围内还有可推进任务，就继续，不因一个非阻塞澄清问题停止全部工作。

## 12. 提交前的交付审查

| 核验 | 对应项 | 通过证据 |
|---|---|---|
| 原创性、赛道、标题与短介绍 | G-05/06；SUB-01/02 | 标题与选题对应；英文blurb词数<10 |

| 五场景 | A-15 | 每个worked example的输入、身份、变更、结果、引用、日志 |
| 架构与信任边界 | A-16 | Mermaid设计已更新为实际实现；导出可展示版本 |
| 源码 | A-16 | 指定commit/标签，可重建，依赖和配置说明，评委可访问 |
| 演示录像 | SUB-06，团队计划交付 | 5–8分钟；不剪掉失败而宣称连续实时；说明加速/模拟 |

最终生成“提交版本说明”：commit、部署版本、模型/配置、源接入状态、测试日期、结果摘要、未完成限制、材料链接。人完成G2后再提交；提交后保存回执。即使继续开发，也保留已经提交版本的可复现状态。
